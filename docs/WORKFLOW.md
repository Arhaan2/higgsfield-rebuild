The phase prompts under docs/prompts are the executable instructions. The coordinator reads the current evidence and continues when a gate passes; phases are not routine permission requests. Keep docs/STATUS.md current. Estimates below are starting budgets; recompute against the actual clock.

## Evidence gates

- **C0:** verified automatic capture for the coordinator in the actual build environment and genuinely independent sessions. Production delegation and worktree use additionally require verified capture for those paths before use. An unavailable, unused delegation route does not invalidate the coordinator's proven capture: keep that dependency explicit and continue eligible coordinator work while resolving it.
- **R1:** required product investigation completed. Blocked flows stay blocked; official documentation is not a completed interaction. Resolve access or get an explicit user decision about a material remaining requirement. If Arhaan changes a requirement, record that decision and retain affected flows as unverified; do not relabel them completed.
- **D2:** the real Apple Design skill has been read and applied, a coherent layout chosen, supported capabilities and shared contracts agreed.
- **V3:** the first real creation path succeeds in the deployed environment.
- **P4:** the intended connected product works, with any material scope change explicitly recorded rather than hidden.
- **Q6:** current implementation passes the critical acceptance checks with evidence.
- **S7:** all actual submission requirements are verified. The video remains pending until Arhaan provides a real recording.

C0 and R1 precede any application implementation. Necessary capture/repository administration is permitted in Phase 0. Templates and this starter packet prove none of the gates.

## Coordination cadence

At each phase start, read current status and the relevant prompt. Establish exclusive paths, contracts and time allowances before delegating. Inspect worker evidence before integration. Root alone handles shared configuration, dependencies, git and deployment. Commit actual phase work and currently available captured logs together; do not squash the development history into a final dump.

After a phase, record the deployed/source revision, observed checks, blockers and next task in docs/STATUS.md. Continue automatically if the next phase's prerequisites hold. A blocker should identify the exact action the user must take and the useful work still possible independently.

## Time management

Get the first deployment online as soon as it is runnable in Phase 3. Prove the high-risk media path before catalog expansion. Freeze extra features when three hours remain. Preserve time for the recording and signed-out access checks. Cut optional models, secondary pages and decorative scope first. Do not save time by inventing evidence or disguising a simulation as working generation.

## Final capture closure

The final assistant response is normally captured after the assistant's last commit. At the end of Phase 7, supply actual-root terminal commands for Arhaan to inspect and commit the final capture update after the agent stops. This last commit is a closure step, not a substitute for incremental logs. Avoid unnecessary additional agent turns after it.
